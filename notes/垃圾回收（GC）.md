## 一、怎么判断一个对象是否“死了”？
### 引用计数法
给每个对象配一个**计数器**:被引用一次 +1,引用失效 -1。**计数为 0 时，表示可回收**。

+ **优点**:简单、高效、判定即时
+ **致命缺陷: 循环引用** (A 引 B、B 引 A,外部都不用了但计数都不为 0,回收不掉)  

###  可达性分析(HotSpot 采用)  
从一组叫 **GC Roots** 的"根对象"出发,沿引用链往下遍历，可达性分析天然解决循环引用的问题:

+ 能从 GC Roots **走到**的对象 ，是**存活的对象**
+ 走不到的对象，表示不可达，这类对象**可回收**

 GC Roots 有哪些 ？

+ **虚拟机栈**中(栈帧局部变量表)引用的对象，也就是正在执行的方法用到的对象
+ **方法区**中类的**静态变量**引用的对象
+ **方法区**中**常量**引用的对象
+ **本地方法栈**中 native 方法引用的对象
+ 还有:被同步锁(synchronized)持有的对象、JVM 内部引用等

### 引用的四种强度
|  引用类型   |  回收时机   | 典型用途 |
| --- | --- | --- |
| **强引用**   | **永不回收**(哪怕 OOM)。Object o = new Object(); |  最普通的引用   |
| **软引用** **SoftReference  ** |  内存够就留;**快 OOM 时**回收   |  做缓存   |
| **弱引用 WeakReference** | **只要发生 GC 就回收**,不管内存够不够   |  ThreadLocal 的 key 等   |
| **虚引用 PhantomReference  ** | ** 完全不影响生命周期,仅用于"对象被回收时收个通知"  ** | 管理堆外内存等 |


## 二、垃圾回收算法
| 算法 | 有碎片吗 | 主要代价 | 适用 |
| --- | --- | --- | --- |
|  标记-清除   | 有 |  效率不稳定   |  (基本不单独用)   |
|  标记-复制   | 无 |  浪费一半空间   | **新生代**(存活率低)   |
|  标记-整理   | 无 | 移动对象成本 | **老年代(存活率高)  ** |


分配内存方案：

+ **标记-清除**算法， 会产生碎片，因此堆不规整，所以分配内存时只能用**空闲列表**
+ **标记-复制 / 标记-整理**， 不会产生碎片，因此堆规整，所以分配可以用**指针碰撞**

## **三、分代收集**
### 堆的分代结构：
```plain
堆
├── 新生代(Young)—— 默认占堆 1/3
│   ├── Eden 区        ┐
│   ├── Survivor 0     ├─ Eden : S0 : S1 = 8 : 1 : 1
│   └── Survivor 1     ┘
└── 老年代(Old)—— 默认占堆 2/3
```

**① 新对象在 Eden 区分配**(绝大多数情况)。

**② Eden 满了 → 触发 Minor GC**(新生代 GC):

+ 用复制算法,把 Eden + 当前 Survivor 里的**存活对象**,复制到**另一个空的 Survivor**
+ 然后 Eden 和刚才那个 Survivor **整个清空**
+ 每熬过一次 Minor GC,对象**年龄 +1**

**③ 对象晋升老年代**:

+ 年龄达到阈值(**默认 15**)→ 晋升老年代
+ **大对象**直接在老年代分配(避免在新生代被复制来复制去)
+ 动态年龄判定:Survivor 里同龄对象总和超过 Survivor 一半,≥该年龄的直接晋升(不用等满 15)

**④ 老年代满了 → 触发 Full GC**。

### 复制算法优化
**解决复制算法浪费 50% 空间的问题**:

+ 不对半分。新生代切成 Eden(80%)+ S0(10%)+ S1(10%)
+ **平时用 Eden + 一个 Survivor(共 90%)**,另一个 Survivor(10%)空着备用
+ Minor GC 时,把这 90% 里的存活对象复制到那个空的 10% Survivor
+ **内存浪费只有 10%,不是 50%**

前提是"新生代存活对象通常不到 10%"(弱分代假说)。万一存活的超过 10%、Survivor 装不下?，使用**分配担保机制**:装不下的直接塞进老年代。

### GC分类
| 类型 |  回收范围   |  特点   |
| --- | --- | --- |
| **Minor GC**(Young GC)   |  只回收**新生代** |  频繁,但快   |
|  Full GC   |  整个堆 + 方法区   |  慢,STW 长,要尽量避免   |


注：GC 工作时(尤其某些阶段),需要**暂停所有用户线程**,叫 **STW**。

+ Minor GC 的 STW 短,影响小
+ **Full GC 的 STW 长**——应用会明显"卡顿",请求堆积

## 四、垃圾收集器
### 收集器的两个指标
a. **吞吐量**(Throughput) = 跑用户代码的时间 ÷(跑用户代码 + GC)的总时间。  
	吞吐量高表示GC占用时间比例低，CPU 更多花在业务上。适合后台计算型任务。

b**. 延迟 / 停顿时间**(Latency)= 单次 GC 造成的 STW 时长。  
	延迟低表示应用卡顿短、更跟手。适合交互型、响应敏感的应用(如 web 服务)。  
	注意:这两个指标常常是矛盾的，要降延迟,往往得让 GC 和用户线程并发跑,这会增加开销、拖低吞吐量。

### 并行 vs 并发
+ **并行(Parallel)**:**多条 GC 线程**同时干活，但**用户线程仍然暂停(STW)**
+ **并发(Concurrent)**:**GC 线程和用户线程同时运行**，GC和业务逻辑并行

### 基础收集器
#### Serial / Serial Old(新生代 / 老年代)
+ **单线程**收集器:GC 时只有一条 GC 线程,而且**必须 STW**
+ 优点:简单,没有多线程切换开销,**单核或小内存场景下反而高效**
+ 现在多用于客户端程序,或作为其他收集器的"后备方案"

#### ParNew(新生代)
+ 就是 **Serial 的多线程版**——多条 GC 线程并行回收新生代,仍然 STW
+ 历史地位:早期**唯一能和 CMS 搭配**的新生代收集器

#### Parallel Scavenge / Parallel Old(新生代 / 老年代)
+ 多线程并行收集
+ 特点:**主打吞吐量**，提供参数可以控制吞吐量目标、最大停顿时间
+ **Parallel Scavenge + Parallel Old 是 JDK 8 的默认收集器组合**

### CMS与G1
#### CMS(Concurrent Mark Sweep，第一个"并发"收集器）
CMS 的目标:**最短停顿时间(低延迟)**。它是第一个让**GC 线程和用户线程并发运行**的收集器,基于"标记-清除"算法。

CMS的4个阶段

| 阶段 | 是否STW | 做什么 |
| --- | --- | --- |
|  ① 初始标记   | **STW**(很短) | 只标记 GC Roots **直接关联**的对象   |
|  ② 并发标记   |  否,并发   | 从上一步出发,遍历整个对象图(**最耗时**)   |
|  ③ 重新标记   | **STW**(较短)   | 修正并发标记期间,因用户线程运行而变动的标记   |
|  ④ 并发清除   | ** 否,并发  ** | 清除垃圾对象   |


**核心**:最耗时的两步(②并发标记、④并发清除)**都和用户线程并发**,只有①③两个**短暂的 STW**。所以 CMS 的停顿大幅缩短。

#### CMS 的 3 个缺点
1. **对 CPU 敏感**:并发阶段 GC 线程要和用户线程抢 CPU,吞吐量下降
2. **浮动垃圾 + Concurrent Mode Failure**:并发清除时用户线程还在产生新垃圾。而且 CMS 不能等老年代满了才回收，因为要预留空间给并发期间的用户线程。**预留不够,就触发 "Concurrent Mode Failure",临时改用 Serial Old 做一次 STW 的 Full GC**，反而会导致长时间停顿
3. **内存碎片**:基于"标记-清除",**会产生碎片**

注意：**JDK 9 标记废弃CMS, JDK 14 已正式移除**。

####   G1(Garbage First，主流，JDK 9+ 默认)  
 G1 的目标:**在用户设定的停顿时间预算内,尽量多回收垃圾**，停顿可预测

##### 打破固定的分代布局,引入 Region
CMS 及之前,新生代/老年代是**固定的物理区域**。G1 不一样:

+ 把整个堆切成**一堆大小相等的独立区域(Region)**
+ 每个 Region **动态扮演**角色
+ **新生代/老年代在 G1 里变成"逻辑概念"**
+ 特大对象放进特殊的 **Humongous Region**

##### Garbage First(垃圾优先)
+ G1 跟踪每个 Region 的"回收价值"(能腾多少空间 vs 花多少时间)
+ 维护一个**优先级列表**
+ 每次回收,**优先回收"垃圾最多、价值最高"的 Region**

##### 可预测的停顿
+ 可以通过设置-XX:MaxGCPauseMillis来设置停顿时间，最大停顿 200ms
+ G1 会在这个时间预算内,挑**合适数量**的 Region 来回收
+ **停顿时间可控、可预测**

##### 不产生碎片
G1 回收时,把存活对象**复制/移动**到其他 Region:

+ 从两个 Region 之间看,是"复制"
+ 从整体看,是"标记-整理"
+ **所以 G1 不产生内存碎片**（这一点完胜CMS）

(G1 的特色回收类型:**Mixed GC**，回收全部新生代 Region + 一部分高价值的老年代 Region。)

#### CMS和G1对比图
| | CMS | G1 |
| --- | --- | --- |
|  内存布局   |  固定分代   | **Region**(动态角色)   |
|  算法   |  标记-清除   |  整体标记-整理   |
|  碎片   |  有   |  无   |
|  停顿时间   |  不可控   |  可预测可设定   |
|  适合堆大小   |  中小堆   |  大堆(几十 GB)   |
|  现状   |  已移除   |  JDK 9+ 默认   |


#### ZGC / Shenandoah——新一代低延迟收集器
这两个是 JDK 11+ 出现的新收集器,目标比 G1 更激进:**极致低延迟**。

**它们解决的问题**:G1 虽然停顿可控,但堆越大、停顿还是会变长。ZGC/Shenandoah 要做到:

+ **STW 停顿降到毫秒级、甚至亚毫秒级**
+ **停顿时间不随堆大小增长**——几 GB 和几 TB 的堆,停顿基本一样

**怎么做到的：**

+ **几乎全程并发**——标记、对象转移、重定位,几乎所有阶段都和用户线程并发,STW 只剩极短的几个点
+ 关键技术:**染色指针**(把标记信息存在指针的某几位上,而不是对象头)+ **读屏障**(读引用时插一段逻辑,保证并发移动对象时引用正确)

## 五、收集器选型
| 场景 | 选择 |
| --- | --- |
|  单核 / 小内存 / 客户端   |  Serial   |
|  后台计算,注重吞吐量   |  Parallel   |
|  大堆,兼顾延迟和吞吐(最常见)   | **G1**(JDK 9+ 默认,主流)   |
|  超大堆 + 要求超低延迟   | ** ZGC / Shenandoah  ** |


## 六、关键问题
1. G1怎么回收巨型对象？
+ 一个对象大小超过单个Region的一半时，就会被判定为 **Humongous Object。**
+ 巨型对象不放进普通的Eden/Old Region, 而是放进专门的**Humongous Region中。**如果一个对象比单个Region还大，那么就用连续的多个Region来存放，这组Region只为这一个对象服务，哪怕对象没占满最后一个Region，剩余空间也不能给别人用。
+ 回收方式是整体释放，不会移动或者复制它，因为成本太高了，所以一旦判定它不可达，就会把它占的那一组Region整个释放掉，类似“标记-清除”
+ 回收时机：
    - 主要在并发标记周期结束时回收死亡的巨型对象
    -  较新版本的 G1 做了优化:**Young GC 也能顺带回收死掉的巨型对象**，因为很多大对象其实也是"短命"的(比如一个大数组,用完就扔),不必非等到老年代回收  
+ 注意点：
    - **空间浪费**:最后一个 Region 没占满,剩余空间闲置  
    - **可能触发 Full GC**:分配巨型对象需要**连续**的多个 Region。如果堆里 Region 比较零散、凑不出足够的连续空间——**可能被迫触发 Full GC** 来腾地方  
    - **调优手段**:如果应用频繁创建大对象,可以**调大 Region 的大小**(`-XX:G1HeapRegionSize`,取值 1MB~32MB、必须是 2 的幂)——Region 大了,更多对象就不会被判定为 Humongous,减少巨型对象带来的麻烦
