## 一、四种基本策略
###  策略 1:先更新 DB,再更新缓存 ❌  
并发问题：

```plain
时刻   线程A             线程B
T1    更新 DB = V1
T2                       更新 DB = V2
T3                       更新缓存 = V2
T4    更新缓存 = V1
结果:DB = V2,缓存 = V1,不一致
```

**还有个浪费问题**:更新的缓存值可能根本没人来读 → 写缓存白做。

**这种方案基本不用。**

### **策略 2:先更新 DB,再删除缓存 **✅**(主流)**
**这是工程上的事实标准****,业界叫 ****Cache-Aside Pattern****(旁路缓存,Facebook 提出)。**

**为什么"删"比"更新"好****:**

+ **删除幂等、简单**
+ **不用计算新缓存值——下次查询时按需重建**
+ **避免了"并发更新缓存"的问题**

**但仍然有一个极端的并发问题**:  

```plain
时刻   线程A(读)              线程B(写)
T1    查缓存,miss(假设刚被淘汰)
T2    从 DB 读到旧值 V1
T3                              更新 DB = V2
T4                              删除缓存(本来就没有)
T5    把 V1 写入缓存
结果:DB = V2,缓存 = V1,不一致
```

**这种不一致的概率极低**,原因——**写操作通常比读操作慢**(要加锁、可能刷盘、可能复制),线程 A "从 DB 读到 V1" 到 "写入缓存" 这个时间窗很短(几毫秒),线程 B 必须正好在这个窗里完成"更新 DB + 删缓存"——**实际几乎不发生**。  

### 策略 3:先删除缓存,再更新 DB ❌
**并发问题(发生概率高得多)**:

```plain
时刻   线程A(写)          线程B(读)
T1    删除缓存
T2                          查缓存,miss
T3                          从 DB 读到旧值 V1
T4                          把 V1 写入缓存
T5    更新 DB = V2
结果:DB = V2,缓存 = V1,**而且会一直不一致直到 TTL 过期**
```

**为什么概率高**:写操作"删缓存"和"更 DB"之间**通常包含一次 DB 写入(几十 ms)**,这个窗口里读操作很容易夹进来。**所以这个方案比"先更 DB 再删缓存"更糟**。  

### 策略 4:延迟双删(防御性补丁)
针对策略 3 的改进——加一次"延迟后再删":

```plain
1. 删除缓存
2. 更新 DB
3. 等待一会儿(比如 500ms)
4. 再次删除缓存
```

第二次删是为了清掉"中间被其他线程读到旧值后写回的缓存"。

**问题**:

+ "等多久"很难定——太短没用,太长影响响应
+ 第二次删除可能失败
+ **延迟期间还是不一致**

**实际很少单独用,只作为某些场景的兜底**。

## 二、关键对比
| |  策略 2(先更 DB 再删缓存)   |  策略 3(先删缓存再更 DB)   |
| --- | --- | --- |
|  不一致触发条件   |  读线程"读 DB"到"写缓存"之间,写线程完成全部操作   |  写线程"删缓存"到"更 DB"之间,读线程完成"读 DB + 写缓存"   |
|  不一致窗口长度   | **几毫秒**(读操作的间隙)   | **几十毫秒**(包含一次 DB 写入)   |
|  触发概率   | 极低   |  明显高   |
|  不一致持续时间   | 短(直到下次写)   |  长(直到 TTL 过期)   |


**核心结论**:**先更 DB 再删缓存,把不一致的窗口"挤到最小"**——这是它成为主流的原因。**不是消除了不一致,是把概率降到几乎为零。**

## **三、 进阶方案:binlog 异步同步缓存  **
**思路**:不要在业务代码里去删缓存,而是**监听 MySQL 的 binlog**——DB 一变化,通过 binlog 触发缓存更新/删除。

**实现**:用 **Canal**、Debezium 等工具订阅 binlog,把"DB 变更"事件投到 MQ,缓存层消费 MQ 来更新缓存。

```plain
应用 → 写 DB
       ↓
       binlog
       ↓
       Canal 订阅
       ↓
       MQ(Kafka 等)
       ↓
       缓存更新服务 → 删 / 更新缓存
```

**优点**:

+ **业务代码完全解耦****——业务代码只管写 DB,不用管缓存**
+ **最终一致性强****——只要 binlog 不丢,缓存最终一定会被更新**
+ **可以处理****失败重试、补偿**

**缺点****:架构复杂,引入额外组件,有几百 ms ~ 几秒的延迟。**

**适合:对一致性要求较高、系统复杂度可以承担的场景。**

## **四、 关键认知:完美一致性不可能  **
**只要 DB 和缓存是两个独立系统,实时强一致几乎不可能做到**。能做的是:

1. **降低不一致的概率**——用"先更 DB 再删缓存"
2. **缩短不一致的窗口**——合理的 TTL 作为兜底
3. **接受最终一致性**(eventually consistent)
4. **实在不行,关键数据不用缓存**——直接走 DB

## 五、实际工程的选择
**中小系统**:

+ 用 **Cache-Aside**(先更 DB 再删缓存)
+ 合理 TTL 兜底
+ 接受偶尔的不一致(概率极低)

**大型系统、一致性要求高**:

+ 用 **binlog 订阅(Canal)** 异步同步缓存
+ 业务与缓存解耦
