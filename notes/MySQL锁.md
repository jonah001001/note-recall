## 锁的两条核心规则
a. RR下，所有当前读默认加Next-Key Lock(行锁+间隙锁)

b.有两种情况下，会退化，不加完整的Next-Key Lock.

① 唯一索引的等值查询命中数据时，会退化为记录锁（Record Lock）

② 等值查询不命中数据时，退化为间隙锁（Gap Lock）

## 7种加锁场景
### 场景1：唯一索引的等值查询，命中数据，会退化为记录锁
```sql
-- 假设 t 的主键是 id,数据有 {5, 10, 15, 20}
SELECT * FROM t WHERE id = 10 FOR UPDATE;
```

加锁结果：只锁住id=10这一行（Record Lock）

退化原因：id是唯一索引，保证id=10最多只有一条，不需要Gap Lock防插入。命中数据时，直接锁这条记	录，不需要锁周围的间隙。

**这个退化是性能优化，锁的粒度越小，并发性越高。**

### 场景2：唯一索引的等值查询，不命中数据，会退化为间隙锁（Gap Lock）
```sql
-- 数据 {5, 10, 15, 20},查 id=12(不存在)
SELECT * FROM t WHERE id = 12 FOR UPDATE;
```

加锁结果：锁住（10，15）这个间隙（Gap Lock）

退化原因：id=12不存在，没有行可以锁，但要防止别人插入id=12的数据，所以需要锁住id=12所在的间隙，也就是（10，15）

**注意：这里虽然只查了id=12的数据，但锁的是（10，15）整个范围，所以想插入id=11，13，14的事务也会被阻塞。**

### 场景3：普通索引等值查询，命中数据时锁不会退化，加Next-Key Lock+Gap Lock
```sql
-- 假设 a 是普通索引,数据 a ∈ {5, 10, 10, 10, 20}(可重复)
SELECT * FROM t WHERE a = 10 FOR UPDATE;
```

加锁结果：

Ⅰ.普通索引a上，加Next-Key Lock(5, 10] + Gap Lock(10, 20)

Ⅱ.主键索引上，加Record Lock(锁住a=10对应的主键行, 如果 a=10 对应多个主键行,每行都加 Record Lock)

不退化原因：普通索引可以有多个相同的值，a=10命中后，也需要加Gap Lock防插入新的a=10。

**注意：普通索引可以再插入相同值,所以 a=10 的命中行,既要锁住前面的间隙(防止 5 后面插入 a=10),又要锁住后面的间隙(防止 20 前面插入 a=10)。前一段用 Next-Key Lock (5, 10](含 10 这行),后一段用纯 Gap Lock (10, 20)(不含 20 这行)。  **

### 场景4：普通索引等值查询，不命中数据，会退化为间隙锁
```sql
-- 假设 a 是普通索引,数据 a ∈ {5, 10, 10, 10, 20}
SELECT * FROM t WHERE a = 13 FOR UPDATE;  -- 13 不存在
```

加锁结果：只在普通索引a上加Gap Lock(10, 20)(纯间隙锁，不锁任何行)，主键索引不加任何锁，因为没有命中具体的行。

退化原因：a=13不存在，但要防止别人插入a=13，所以加间隙锁（10，20）

**注意：如果是查a=30，那么会在普通索引a上加Next-Key Lock，锁的范围是（20，supremum），但supremum是伪记录，所以此时的Next-Key Lock和纯Gap Lock没有什么区别，见下图。**

### 场景5：主键范围查询，会对扫描过程中遇到的每一条记录都加Next-Key Lock
```sql
-- 假设主键 id,数据 {5, 10, 15, 20, 25}
SELECT * FROM t WHERE id > 10 AND id <= 20 FOR UPDATE;
```

加锁结果看MySQL版本，如果是MySQL 5.7，在扫描时，会对过程中遇到的每条记录都加Next-Key Lock，直到遇到第一条不符合条件的数据位置，此时加锁范围为：（10，25]。如果是MySQL 8.0+，对范围查询做了优化，如果有明确的上界，且上界存在时，InnoDB扫描到上界后就停止，不再向后多访问一条记录，因此最终的加锁范围是：（10，20]，如下图：

### 场景6：普通索引范围查询，会同时在普通索引和主键索引上加锁
```sql
-- 数据范围：(5, 50)  (10, 100)  (15, 150)  (20, 200)  (25, 250)
SELECT * FROM t WHERE a >= 100 AND a < 200 FOR UPDATE;
```

加锁结果：

普通索引 idx_a加锁（50，200]。 

主键索引锁id=10和id=15

注意：查询范围是[100, 200)，但是在a=100时命中了数据，加Next-Key Lock，要包含前面的间隙，也就是（50，100）这一段，所以idx_a整体加锁范围就是（50，200]，但是主键索引只锁了id=10和id=15，见下图：

为什么idx_a要锁200呢，200并不在查询范围内？**根据前面的RR加锁原则， InnoDB 加锁的默认单位就是 Next-Key Lock,而 Next-Key Lock = 间隙 + 记录,是一个不可分割的整体**，**等值查询时会有边界退化，而范围查询没有，所以还是默认的Next-Key Lock。**

insert探测法验证，a=80，在（50，100）范围内，会被阻塞，表示这一段也被加锁了，a=200, 也被阻塞，表明这条记录也被锁了。

### 场景7：无索引查询
```sql
SELECT * FROM t WHERE b = 'xx' FOR UPDATE;   -- b 列没有索引
```

加锁结果：扫描到的每一行都加Next-Key Lock

加锁原因：b列没有索引，所以InnoDB无法根据索引定位，等价于全表扫描，这种场景下，会扫描聚簇索引的每一行，RR下，会给每一行都加Next-Key Lock, 最后导致表的每一行，每一个间隙都被锁，等价于锁了整张表。



总结：

| 场景 | 索引 | 查询 | 命中 | 加锁结果 |
| --- | --- | --- | --- | --- |
| 1 | 唯一索引 | 等值 | 命中 |  退化为 **Record Lock**(只锁行)   |
| 2 | 唯一索引 | 等值 | 不命中 | 退化为 **Gap Lock**(只锁间隙) |
| 3 | 普通索引 | 等值 | 命中 | **Next-Key Lock + Gap Lock**(两段)+ 主键 Record Lock   |
| 4 | 普通索引 | 等值 | 不命中 |  退化为 **Gap Lock** |
| 5 | 主键 | 范围 | - |  聚簇索引上**连续的 Next-Key Lock 区间** |
| 6 |  普通索引   | 范围 | - |  普通索引上**区间** + 主键上**离散 Record Lock** |
| 7 |  无索引   | 任意 | - |  全表 Next-Key Lock ≈ 锁全表   |


**两条主线规律**:

**① 退化只发生在"唯一索引"**——唯一性保证不能重复插入,所以可以不要间隙锁

**② 不命中 → 退化为纯 Gap Lock**(没有行可锁,只防插入)

**③ 其他所有情况 → 默认 Next-Key Lock**

tips: 唯一索引范围查询可以通过场景5+场景6推导出来，不另外研究。
