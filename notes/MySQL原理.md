## 一、InnoDB 索引结构相关
### 1. 为什么 InnoDB 用 B+ 树不用 B 树？
InnoDB索引的数据结构是B+树，为什么不用B树呢？首先明确 B+ 树与 B 树的核心区别：

+ B+ 树：仅叶子节点存储数据，其他非叶子节点仅存储索引值；所有叶子节点通过双向链表串联，形成有序结构。
+ B 树：所有节点（非叶子节点+叶子节点）均存储数据；叶子节点之间相互独立，无关联。

基于上述区别，B+ 树相对 B 树的优势的在于，更适配 MySQL 的数据查询场景：

+ ① 减少磁盘 IO 次数：B+ 树非叶子节点不存数据，仅存索引，因此单个节点可存储更多索引值，使得树的高度更矮（通常为3层），查询一行数据所需的磁盘 IO 次数更少（3次左右），效率更高。
+ ② 范围查询更高效：找到范围查询的起始叶子节点后，无需回溯到根节点，可直接通过叶子节点的双向链表依次遍历后续节点，快速获取所有符合条件的数据；而 B 树需要频繁回溯祖先节点，效率较低。
+ ③ 全表扫描效率更高：B+ 树的叶子节点是有序双向链表，全表扫描时只需按链表顺序读取即可，磁盘 IO 利用率最高；而 B 树需逐个节点遍历，IO 效率低。

### 2. 为什么 InnoDB 推荐主键用自增整数（BIGINT AUTO_INCREMENT），不用 UUID？
核心原因是自增主键更适配 InnoDB 聚簇索引的特性，能提升性能、减少开销，具体优势如下：

+ ① 避免页分裂：InnoDB 聚簇索引的叶子节点按主键物理顺序排序，自增主键的新数据永远追加到叶子节点末尾，不会破坏原有排序，避免触发大量页分裂（页分裂会导致磁盘碎片，降低查询效率）；而 UUID 是随机字符串，插入位置随机，会频繁触发页分裂。
+ ② 提升 Buffer Pool 命中率：自增主键的插入集中在叶子节点的最后几页，热点数据固定，Buffer Pool（缓存）能高效缓存这些热点页；而 UUID 插入位置随机，会导致缓存页频繁替换，缓存命中率大幅下降，甚至冲垮缓存。
+ ③ 减少空间开销：UUID 长度为36个字符，占用更多存储空间；而 BIGINT 仅占8个字节。此外，InnoDB 所有二级索引的叶子节点都会存储主键值，主键越大，所有二级索引的存储空间会同步膨胀，增加磁盘负担。

## 二、SQL 查询相关
### 3. SELECT * FROM t WHERE a = 50 这条 SQL 用了几次 IO？
分理论值和实际值，核心取决于 Buffer Pool 的缓存作用：

+ 理论 IO 次数：6次。假设二级索引和主键索引均为3层 B+ 树，查询时需先通过二级索引查找（3次 IO），找到对应主键后，再通过主键索引回表查询完整数据（3次 IO），合计6次。
+ 实际 IO 次数：2次。Buffer Pool 会缓存 B+ 树的非叶子节点（索引节点），无需触发物理 IO；仅需对二级索引的叶子节点和主键索引的叶子节点进行物理 IO，合计2次（一次二级索引叶子节点，一次回表后的主键叶子节点）。

## 三、Explain Extra 字段解析
### 4. Explain Extra 常见的有几种？分别是什么含义？
Explain 的 Extra 字段用于展示 SQL 执行过程中的额外信息，常见类型及含义如下表所示：

| **Extra 显示内容** | **真实含义** |
| --- | --- |
| Using index | 覆盖索引——查询的所有列都能从索引中获取，无需回表查询主键索引 |
| Using where | 存储引擎返回数据后，MySQL Server 层对数据进行进一步过滤（索引无法过滤全部条件） |
| Using index condition | 索引下推（ICP）——MySQL 8.0 默认开启，将部分过滤条件下推到存储引擎，减少回表次数 |
| Using filesort | 需要进行磁盘排序（未使用索引排序，效率较低） |
| Using temporary | 查询过程中使用了临时表（如分组、排序时无合适索引，效率较低） |
| Using join buffer | 多表连接时，使用连接缓冲区（join buffer）优化连接效率 |
| （空 / NULL） | 查询使用了索引，但需要回表查询完整数据（非覆盖索引场景） |
