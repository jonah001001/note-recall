# Redis三大经典问题

##  一、缓存穿透(Cache Penetration)  
**定义**:查询**根本不存在**的数据。每次请求都缓存 miss → **全部打到 DB**。

**触发场景**:

+ **恶意攻击**:用大量不存在的 key(`id=-1`、`id=99999999`)疯狂查,绕过缓存,把 DB 压垮
+ **业务漏洞**:某些查询条件本身就大概率没数据

**核心矛盾**:**缓存只能缓存"存在的数据",对"不存在的查询"无能为力**。

**解法 1:缓存空对象**

DB 查不到,**也在缓存里写一个 "null" 标记**。下次同样的 key,直接从缓存返回 null,不打 DB。

+ **缺点**:占缓存空间。**设较短 TTL**(1-5 分钟)避免大量无用 key 长期占用

**解法 2:布隆过滤器(Bloom Filter)**

在缓存前加一个**布隆过滤器**,**预先记录所有"可能存在的 key"**:

+ 请求来了**先查布隆过滤器**
+ **不在过滤器里 → 直接拒绝**(不打缓存也不打 DB)
+ 在过滤器里 → 继续走缓存

**布隆过滤器原理**:

+ 一个**大位数组** + **多个哈希函数**
+ 存入:对 key 做多次哈希,把对应位置的 bit 设为 1
+ 查询:同样的哈希,**任何一个位置是 0,key 一定不存在**;**所有位置都是 1,key 可能存在**(可能哈希冲突)
+ **不会假阴性,但有假阳性**——它能 100% 排除"不存在",但"存在"的判断不一定准

## 二、缓存击穿(Cache Breakdown)
**定义**:**某个热点 key**(高并发访问)在缓存里**突然过期**,瞬间大量请求**穿透到 DB**。

**和"穿透"的区别**(容易混):

+ **穿透**:查"不存在"的数据,问题在**查询本身**
+ **击穿**:**热点 key 过期**,瞬间 DB 被打爆——key 是存在的,只是缓存里没了

**经典场景**:促销商品页,10 万 QPS。缓存设 1 小时过期——**过期那一瞬间,10 万请求全部 miss,全部打到 DB,DB 直接挂**。

**解法 1:互斥锁**

缓存 miss 时,**只允许一个请求去查 DB + 重建缓存**,其他请求等待:

+ 用 Redis 的 `SETNX` 或本地锁,**第一个请求**拿到锁去查 DB
+ **其他请求**等待 / 短暂自旋
+ 重建完缓存后,其他请求从缓存拿到数据

**效果**:并发 10 万的瞬间,**只有 1 个请求打到 DB**。

**解法 2:热点数据永不过期**

对极少数核心热点 key,**不设 TTL,永不过期**。

+ **怎么更新**?**逻辑过期**——值里存一个"逻辑过期时间",访问时或定时任务**异步更新缓存**(不让用户请求等待)

## 三、缓存雪崩(Cache Avalanche)
**定义**:**大量 key 同时过期**(或 **Redis 整体宕机**),瞬间大量请求打 DB。

**和"击穿"的区别**:

+ **击穿**:**一个**热点 key 过期
+ **雪崩**:**大量** key 同时过期,或 Redis 服务器整体挂

**触发场景**:

+ 一批 key 用了**相同的 TTL**(比如启动时批量 set,都设 1 小时)→ 同时过期
+ Redis 宕机,所有缓存集体失效

解法

**1. TTL 随机化**——别给一批 key 设一样的 TTL,**加随机抖动**(1 小时 ± 5 分钟)。让过期时间错开,避免集中失效。

**2. 多级缓存**——Redis 之上再加**应用层本地缓存**(如 Caffeine)。Redis 挂了,本地缓存还能扛一阵。

**3. 熔断 + 降级**——DB 压力大时**触发熔断**,直接返回降级数据(默认值、空、旧缓存)。保护 DB 不被压垮。

**4. Redis 高可用**——主从 + 哨兵 / Cluster,保证 Redis 本身不挂。

## 四、三者对比
| | 穿透 | 击穿 | 雪崩 |
| --- | --- | --- | --- |
| 触发 | 查不存在的 key   | **单个**热点 key 过期   | **大量** key 同时过期 / Redis 挂   |
| 范围 | 持续 / 定向   | 突发 / 单点   | 大规模   |
| 核心解法 | 缓存空对象 / 布隆过滤器   | 互斥锁 / 永不过期   | TTL 随机化 / 熔断 / 高可用   |
