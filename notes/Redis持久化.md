# Redis持久化
## 一、RDB（快照）
### **核心思想**
**把某个时刻的内存数据，整个“拍快照”存到磁盘**，文件名叫dump.rdb(二进制文件)

### 触发方式
    - **SAVE**(手动)，在主线程同步执行，会阻塞所有请求（因为Redis是单线程），所以**生产环境禁用。**
    - **BGSAVE(**手动/自动触发**)，**fork子进程异步处理，不阻塞主线程
    - **自动触发**：配置save m n（m秒内有n次修改就触发BGSAVE），默认有几组（900 1，300 10，60 10000）

### 关键机制：fork+写时复制（COW）
fork后，父子进程共享同一份物理内存，只读时共享，不复制，某一方要写某个内存页时，操作系统把复制这页，让写的那方改自己的副本。

代价是父进程的写操作会让被写的内存页被复制，短暂增加内存占用。

### RDB的取舍
优点：文件紧凑，恢复快，适合做备份容灾

缺点：会丢数据，两次RDB之间的修改，宕机会丢失

## 二、AOF（追加日志）
### 核心思想
**每条写命令追加到日志文件。**重启时重新执行一遍这些命令，数据就可以恢复，文件名叫appendonly.aof(文本文件)。

### 写入策略
与MySQL的redo log类似，AOF的写入流程是：执行写命令 -> 写入AOF缓冲区（内存）-> 按fsync策略刷盘

fysnc策略：

| 值 | 行为 | 数据安全性 |
| --- | --- | --- |
| always | 每次写命令都fsync | 最安全（几乎不丢） |
| everysec(默认) | 每秒fsync一次 | 折中，最多丢一秒数据 |
| no | 不主动fsync, 听OS的 | 性能最好，可能丢很多 |


### AOF重写
AOF是一直追加的，文件会越写越大，所以，AOF重写，就是**根据当前内存状态，生成一份最小的命令集**，目的是恢复出同样的数据，并大幅减少命令数。（如100条incr count重写为set count 100）

重写机制（类似BGSAVE）：

+ 重写也是 **fork 子进程**做，不阻塞主线程
+ 重写期间,主线程产生的新命令,会**同时写到旧 AOF 和"重写缓冲区"**
+ 重写完成,**把重写缓冲区的命令追加到新 AOF 末尾**
+ 用新 AOF 替换旧 AOF

**自动触发**:AOF 比上次重写后大了 100% **且** 至少 64MB 时触发，目的是避免文件还很小时频繁重写。 

## 三、RDB vs AOF
|  | RDB | AOF |
| --- | --- | --- |
| 形式 | 二进制快照 | 命令日志（追加） |
| 文件大小 | 紧凑，小 | 较大 |
| 数据安全 | 较弱（丢失两次快照之间的数据） | 强（默认最多丢1秒的数据） |
| 恢复速度 | 快（直接加载二进制） | 慢（要重放所有命令） |
| 适合场景 | 备份，容灾 | 实时性要求高 |


## 四、混合持久化（Redis 4.0引入）
 AOF 文件的**开头是 RDB 格式**,**后面是增量的 AOF 命令**。  

**开启后,AOF 重写时**:

+ 子进程先把当前内存用 **RDB 格式**写到新 AOF 文件**开头**
+ 重写期间新增的命令,用 **AOF 文本格式**追加到后面

**恢复时**:

+ 先加载 RDB 部分(快)
+ 再重放后面的 AOF 增量(量小,也快)

**这是 4.0+ 推荐方式**——兼顾 RDB 的恢复速度和 AOF 的数据安全。
