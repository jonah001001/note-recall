# Redis数据结构
## 一、对象机制
### **Redis 里,每个 value 都被封装成一个 redisObject 对象,它有几个关键字段:  **
+ **type**:对象类型——就是那 5 种(String/List/Hash/Set/ZSet)
+ **encoding**:编码——这个对象**底层用什么数据结构实现**
+ **ptr**:指向底层数据结构的指针
+ (还有 refcount 引用计数、lru 用于内存淘汰等)

** 注意：一种 type,底层可以有多种 encoding。  **

| 类型type | 可能的底层编码 encoding |
| --- | --- |
|  String   |  int / embstr / raw   |
|  List   |  quicklist(新版)   |
|  Hash   |  listpack(数据少) / hashtable(数据多)   |
| Set | intset / listpack / hashtable |
| Zset | listpack(数据少) / skiplist + hashtable(数据多) |


**为什么要"type 和 encoding 分离"**: 让 Redis 能在不同场景用**最优的底层结构**。 比如，一个 Hash,数据少时用紧凑的 listpack(省内存),数据一多自动转成 hashtable(查得快)。  

## **二、String 类型的三种编码  **
String 能存文本、整数、浮点数,甚至二进制数据(图片),最大 512MB。它有**三种编码**:

+ **int**:存的是整数、且能用 long 表示 → 直接把整数存在对象里
+ **embstr**:字符串,且长度较短(约 ≤ 44 字节) → embstr 编码
+ **raw**:字符串较长(> 约 44 字节) → raw 编码

embstr 和 raw 都用 **SDS** 存字符串,区别在内存分配:

+ **embstr**:redisObject 和 SDS **一次性分配在连续内存**(一次 malloc)——短字符串用,分配/释放快、对 CPU 缓存友好
+ **raw**:两者**分两次独立分配**(两次 malloc)

### ** SDS:Redis 自己造的字符串  **
|  C 字符串的问题   | SDS 的解决 |
| --- | --- |
| **获取长度 O(n)**，不记长度,要数到 \0 | SDS有len字段记录长度 → **获取长度 O(1)** |
| **缓冲区溢出风险**——拼接时空间不够会溢出   | SDS有alloc 字段记已分配空间 → 修改前先检查,**杜绝溢出** |
| **二进制不安全**——靠\0判断结尾,中间不能有\0 | SDS靠len判断结尾 → 中间可放任意字节 → **能存二进制数据** |
| ** 频繁重新分配内存  ** |  空间预分配 + 惰性释放   |


**SDS 的"空间预分配 + 惰性释放"**:

+ **预分配**:扩容时,不只分配刚好够的,还**多预留一些** → 减少未来扩容的内存分配次数
+ **惰性释放**:字符串缩短时,**不立即释放**多出来的空间,先留着备用(用 alloc - len记着)

**还有个细节**——SDS 末尾也会加一个 \0 (但**不计入 len**),这样能复用一部分 C 的字符串函数。而且 Redis 为了抠内存,SDS 分了好几种 header 类型(sdshdr5/8/16/32/64),**短字符串用小 header**,能省一字节是一字节——这是 Redis "对内存极致抠"的风格。

## 三、基础数据结构
###  listpack  
+ Hash、Set、ZSet 在**数据量小**时,都想用一种"紧凑省内存"的结构存，这个结构就是 **listpack(紧凑列表)**。 
+ **listpack是一块连续内存**,**把多个元素紧凑地依次排列。省内存(无指针开销)、适合元素少且小的场景。代价是查询 O(n)(要遍历)，所以只用于小数据量。  **
+ ** **listpack 是 Redis 7.0 引入的,用来取代老的 ziplist  

注：版本演进：ziplist "连锁更新"，每个节点记录"前一个节点的长度",如果某节点长度变了,可能引发后面一连串节点跟着更新,最坏 O(n²)。listpack 重新设计,每个元素不再依赖前一个元素的长度,消除了连锁更新。

### List —— quicklist
有序的字符串列表,两端可 push/pop,能当队列/栈用。

**底层编码:quicklist**(3.2 之后)。

**quicklist = 双向链表 + listpack**, 它是个双向链表,但**链表的每个节点是一个 listpack**(节点内紧凑存一批元素)。

**为什么这样设计**(折中):

+ 纯链表:一个元素一个节点,指针开销大、内存碎片多
+ 纯 listpack:一整块连续内存,数据量大时插入/删除要移动大量内存,大块连续内存也难分配
+ **quicklist 折中**:节点之间靠链表指针(灵活),节点内部用 listpack(紧凑)——一个节点装一批元素,而不是一个元素一个节点

###  Hash —— listpack / hashtable  
**Hash**:存 field-value 对,像个小 map。

**两种编码**:

+ 数据量小 → **listpack**
+ 数据量大 → **hashtable**(Redis 的 dict)

**转换条件**:字段数超过 128(hash-max-listpack-entries),或某个值长度超过 64 字节(hash-max-listpack-value)→ listpack 转 hashtable。

###  Set —— intset / listpack / hashtable  
**Set**:无序、不重复的字符串集合。

**三种编码**:

+ 元素**全是整数**且数量少 → **intset**(整数集合)
+ 有非整数、但数量少 → **listpack**
+ 数量大 → **hashtable**

**intset**:专存整数的紧凑结构,内部**有序排列**(便于二分查找),还会根据整数大小自动升级(int16→int32→int64)。

###  ZSet —— listpack / skiplist + hashtable  
**ZSet(有序集合)**:每个元素带一个 score(分数),按 score 排序。Redis 最有特色的类型——排行榜、范围查询全靠它。

**两种编码**:

+ 数据量小 → **listpack**
+ 数据量大 → **skiplist(跳表) + hashtable**,**两个结构一起用**

**为什么大数据量要两个结构配合**:

+ **跳表**:元素按 score 排序 → 擅长**范围查询、按排名查**(ZRANGE)
+ **哈希表**:存 member → score 映射 → 擅长**按成员 O(1) 查分数**(ZSCORE)

ZSet 这两种查询都高频,所以同时维护两个结构,各发挥所长——**用空间换时间**。

## 四、跳表（skiplist）
1. 定义：

跳表是一种**有序**的数据结构,基于**多层链表**实现,平均查找 O(log n)。  

2. 结构：
+ **最底层**是一个完整的有序链表,包含所有元素
+ 之上建多层**稀疏索引**——每层是下一层的"抽样"(大约每隔一个提取一个到上层)
+ 查找时**从最高层开始**,能"跳过"大量元素快速逼近目标,再逐层下降

```plain
L3:  1 ──────────────→ 17
L2:  1 ──────→ 9 ────→ 17 ──────→ 25
L1:  1 → 5 → 9 → 13 → 17 → 21 → 25 → 29   (完整链表)
```

3. 为什么Zset用跳表，而不用红黑树？
+ **范围查询天然方便**:ZSet 高频做范围查询(ZRANGE)。跳表**最底层就是有序链表**,找到范围起点后,**顺着链表往后遍历**就行。红黑树做范围查询要中序遍历,麻烦得多。
+ **实现简单**:跳表的插入/删除只需改几个指针 + 随机定层数,**不需要像红黑树那样旋转、变色维持平衡**。代码简单 = 少 bug、好维护。
+ **性能相当**:跳表查找/插入/删除平均都是 O(log n),和平衡树一个量级。

## 五、dict(哈希表)
1. 结构：
+ 一个 dict 里有**两个哈希表 ht[0] 和 ht[1]**——平时只用 ht[0],**ht[1] 是给 rehash 用的**
+ 每个哈希表是个数组,每个槽位指向一个链表——**用链地址法解决哈希冲突**(算出同一下标的 key,挂在同一槽位的链表上)
2. **rehash(扩容/缩容)**:
+ 负载因子 = 元素数 / 表大小
+ 负载因子太大(冲突多、链表长、查询慢)→ **扩容**;太小 → 缩容省内存
+ rehash = 换一个新大小的表,把所有元素重新分布
3. 如果 dict 里有几百万个 key,rehash 时**一次性**把所有 key 搬到新表，但Redis 是**单线程**,这个大操作会**长时间阻塞**所有请求，该怎么处理？

**解法:渐进式 rehash，不一次搬完,分多次渐进地搬**:

    1. rehash 开始,给 **ht[1]** 分配新空间
    2. dict 里维护一个 **rehashidx**,记录"搬到哪了"
    3. **接下来每次对 dict 的增删改查,顺带把 ht[0] 上一个槽位的节点搬到 ht[1]**,rehashidx++
    4. (定时任务也会搬一点)
    5. 直到 ht[0] 搬空,rehash 结束,ht[1] 变成 ht[0]

**rehash 期间的两个细节**:

    - **查询**:先查 ht[0],没找到再查 ht[1]
    - **新增**:新元素**直接加到 ht[1]**——保证 ht[0] 只减不增,最终能搬空

**渐进式 rehash 的本质**:把一个"集中的大耗时操作",**分摊到很多次小操作里**。
