## 一、过期键的删除
| 策略 | 怎么做 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 定时删除 | 每个key配一个定时器，到点删除 | 内存友好 | CPU杀手，大量的定时器会抢占主线程 |
| 惰性删除 | 不主动删，访问时检查+删除 | CPU友好 | 没被访问到的过期key永远留在内存里 |
| 定期删除 | 周期性随机抽样检查+删除 | 折中 | 不能保证及时清掉所有的过期key |


**定时删除被 Redis 放弃**(对 CPU 不友好,违背单线程哲学)。

**Redis 实际用的:惰性删除 + 定期删除(互补)**

**惰性删除**:每次访问 key,先检查 TTL。过期 → 立即删,返回"不存在"。

**定期删除**:Redis 默认**每 100ms** 执行一次:

1. 从设了 TTL 的 key 里**随机抽一批**(比如 20 个)
2. 过期的就删
3. 如果**这批里过期比例超过 25%**,**再抽一批**继续删
4. **整体时间不超过 25ms**(避免长时间阻塞主线程)

**两者互补**:

+ **惰性删除**保证"被访问的过期 key 一定被清"
+ **定期删除**保证"没被访问的过期 key 也有机会被清"
+ **都没清掉的**?→ 下面"内存淘汰"作最后兜底

## 二、内存淘汰
8种淘汰策略

| 策略 | 范围 | 依据 |
| --- | --- | --- |
| **noeviction**(默认)   | - | **不淘汰**,写满后返回错误   |
|  allkeys-lru   | 所有 key |  LRU   |
|  allkeys-lfu   | 所有 key   |  LFU   |
|  allkeys-random   | 所有 key |  随机   |
|  volatile-lru   | 有 TTL 的   |  LRU   |
|  volatile-lfu   | 有 TTL 的   |  LFU   |
|  volatile-random   | 有 TTL 的   |  随机   |
|  volatile-ttl   |  有 TTL 的   |  TTL 短的优先   |


**默认 noeviction**,但**生产几乎不用默认**——内存满了 Redis 就拒绝写入,等于"假死"。生产常用 **allkeys-lru** 或 **allkeys-lfu**。

**LRU vs LFU **

+ **LRU**(最近最少使用):**最常用**。但有个缺陷——**偶尔扫描一次的冷数据,会把真热点挤掉**(比如批量任务把一堆冷 key 刷成"最近访问过")
+ **LFU**(最近最少频率,Redis 4.0 引入):看的是"访问频率",**更能准确反映热度**。适合**访问频率分布很不均**的场景

## 三、 Redis LRU 实现细节
**真 LRU 的标准实现**:维护一个全局链表,按访问时间排序——访问 key 就移到表头,淘汰从尾部淘汰。  

**Redis 的做法:近似 LRU**

+ 每个 key 的对象头里有个 lru 字段(24 bits),**记录最后访问时间戳**
+ 淘汰时,**随机抽 N 个 key**(默认 5),从里面挑 lru 字段最旧的那个淘汰
+ 样本数可调(maxmemory-samples),**样本越大越接近真 LRU,但越耗 CPU**

**核心思路**:**用"随机抽样 + 局部比较"代替"全局排序"——用一点精度换巨大的性能提升**。

LFU 同理,也是**近似实现**(用同一个字段存"对数计数器"型的频率估计)。  

## 四、过期 key 对持久化的影响(细节)  
+ **RDB**:过期 key **不写进** RDB 文件
+ **AOF**:key 过期时,会**追加一条 DEL 命令**——保证 AOF 重放时也会删
+ **AOF 重写**:过期 key **不写进**新 AOF
