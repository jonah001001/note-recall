## 二、监控与故障处理工具
| 工具 | 作用 | 典型场景 |
| --- | --- | --- |
| jps | 列出所有 Java 进程和 PID | 第一步,先找到要查的进程 |
| jstat   | 看 GC 统计(各代使用率、GC 次数/耗时)   | 看 GC 是否频繁、各代涨势   |

## 三、调优实战
### 开启GC日志
 JDK 8 及之前: -XX:+PrintGCDetails -Xloggc:gc.log

 JDK 9+:统一成 : -Xlog:gc*:file=gc.log

**GC 日志能告诉你**:每次 GC 的类型(Young/Full)、GC 前后各代内存变化、单次 GC 耗时。**通过它能判断**:GC 是否过于频繁、单次是否太久、Full GC 为什么触发、有没有泄漏迹象(**每次 GC 后老年代不降反升 = 危险信号**)。  

### 读GC日志
#### 2.1 读Young GC日志
```plain
2026-05-19T10:23:45.123+0800: 3.456: [GC (Allocation Failure) 
[PSYoungGen: 76800K->10240K(89600K)] 150000K->83448K(294400K), 0.0123456 secs] 
[Times: user=0.04 sys=0.01, real=0.02 secs]
```

| 片段 | 含义 |
| --- | --- |
|  2026-05-19T10:23:45.123   |  GC 发生的日期时间   |
|  3.456   |  JVM 启动后第 3.456 秒发生   |
|  GC   |  是 Minor GC(Young GC);如果是 Full 会写 Full GC |
|  (Allocation Failure)   | **触发原因**:Eden 放不下新对象了。这是 Young GC 最常见的触发原因   |
|  PSYoungGen: 76800K->10240K(89600K)     | **新生代**:GC前 76800K → GC后 10240K,总容量 89600K   |
|  150000K->83448K(294400K)   | **整个堆**:GC前 150000K → GC后 83448K,总容量 294400K   |
|  0.0123456 secs   |  这次 GC 耗时(STW 时长)   |
|  [Times: user/sys/real]   |  CPU 时间:用户态 / 内核态 / 实际墙钟时间   |


怎么算晋升量？

新生代回收了:76800 - 10240 = 66560K， 整个堆回收了:150000 - 83448 = 66552K，两者的差值 = 66560 - 66552 = 8K， 这 8K 就是"晋升到老年代"的对象。

原因：新生代清掉的对象,要么是真垃圾(被回收),要么是存活对象(被挪走)。整个堆少回收的那部分,就是"没真回收掉、只是从新生代挪到老年代"的——也就是晋升量。  

还能看出:GC 后老年代占用 = 83448 - 10240 = 73208K 。

关于 Times 那行: user+sys 通常 大于 real** **,因为多个 GC 线程并行,多核 CPU 时间累加。反过来,如果 real 明显大于user+sys,是危险信号,  说明 GC 在等待(IO 阻塞、CPU 被抢、内存换页 swap)。  

#### 2.2  读 Full GC 日志
```plain
2026-05-19T10:30:12.456+0800: 390.789: [Full GC (Ergonomics) 
[PSYoungGen: 10240K->0K(89600K)] [ParOldGen: 200000K->180000K(204800K)] 
210240K->180000K(294400K), [Metaspace: 35000K->35000K(1079296K)], 
1.2345678 secs] [Times: user=3.5 sys=0.1, real=1.2 secs]
```

+ Full GC (Ergonomics): Full GC,原因是 JVM 自适应判断。其他常见原因: (Metadata GC Threshold)=元空间不足、(System.gc())=代码显式调用
+ PSYoungGen: 10240K->0K: Full GC 会清新生代,**新生代被清空到 0**
+ ParOldGen: 200000K->180000K(204800K): **老年代**——GC前 200000K,容量 204800K
+ Metaspace: 35000K->35000K: 元空间。Full GC 一般回收不动类信息,这里没变化
+ 1.2345678 secs: **这次 Full GC 耗时 1.2 秒**——应用整整卡了 1.2 秒

暴漏的问题：

+ 老年代 GC 前 200000K / 容量 204800K → **占用 97%,快满了**,这就是为什么触发 Full GC
+ 老年代 GC 后还有 180000K → **回收只降了 20M,效果很差**,老年代还占 88%
+ **回收完还占 88% + 单次 1.2 秒** → 这是一个不健康的信号:**老年代里大量对象回收不掉**,要么堆太小,要么内存泄漏

#### 2.3  怎么从 GC 日志分析问题  
##### 健康的 GC 日志长这样
        * Young GC:频率不高(几秒~几十秒一次)、单次耗时短(几~几十毫秒)、回收后新生代基本清空
        * Full GC:很少发生(几小时/几天一次,甚至基本不发生)
        * 老年代:GC 后能稳定在某个水平,**不持续增长**

##### 六个"有问题"的信号
        1. **频繁 Full GC**:Full GC 一会儿一次 → 严重问题
        2. **内存泄漏迹象**:连续多次 GC,**老年代 GC 后的占用一次比一次高**,Full GC 也压不下去 → 泄漏
        3. **单次 GC 耗时过长**:Young GC 超几百毫秒、Full GC 好几秒 → STW 太长
        4. **Young GC 太频繁**:几百毫秒就一次 → 新生代太小 / 对象创建太快
        5. **晋升过快**:每次 Young GC 后晋升量很大(新生代回收量 ≫ 整堆回收量,差值大)→ 对象过早进老年代,会加速老年代填满 → 引发频繁 Full GC
        6. `**real**`** ≫ **`**user+sys**`:GC 时系统有别的瓶颈(IO/CPU/swap)

##### 分析的核心指标
GC 频率、单次 GC 耗时、GC 吞吐量(GC 时间占比)、**老年代 GC 后占用的趋势**(判断泄漏的关键)、晋升速率。

### 四类经典问题排查
#### 2.1 堆OOM （OutOfMemoryError: Java heap space）
常见原因： ① 内存真不够(堆设小了)    ② **内存泄漏**(对象本该回收,却被意外引用着)  

排查： jmap导出heap dump,  然后用MAT分析，看哪类对象占用最多、引用链是谁。

#### 2.2 内存泄漏
定义:对象不再使用,但还被某个 GC Roots 可达的引用**持有着**,GC 回收不掉。    

常见原因：

        * 静态集合(static List/Map)只加不删
        * 资源(连接、流)没关闭
        * 监听器/回调没注销
        * ThreadLocal 用完没remove()
    - 表现： 老年代持续增长 → 频繁 Full GC → 最终 OOM  
    - 排查： MAT 分析 heap dump,顺着引用链找到那个"不该存在"的引用。  

#### 2.3 CPU飙高
排查思路：

```plain
① top              → 找到 CPU 高的 Java 进程 PID
② top -Hp <pid>    → 找到该进程里 CPU 高的线程 TID
③ printf '%x' <TID> → 线程 TID 转成 16 进制
④ jstack <pid>     → 导出线程栈,搜那个 16 进制 TID,看它在执行什么
```

**常见原因**:死循环、频繁 GC(GC 线程吃 CPU)、大量计算。  

#### 2.4 频繁FullGC
**危害**:Full GC 的 STW 长,频繁 Full GC = 应用频繁卡顿。

**常见原因**:老年代空间不足(堆小 / 内存泄漏填满老年代)、元空间不足(加载类太多)、大对象频繁进老年代、代码里显式 `System.gc()`。

**排查**:jstat 看 GC 频率,GC 日志看触发原因。

### 调优方法论
+ **先监控定位,再动手调**——别上来就改参数。先用工具找到问题在哪
+ **大多数 JVM 问题,最终是"内存"和"GC"问题**
+ **很多"JVM 问题"其实是代码问题**——内存泄漏、不合理的对象创建。**调参数治标,改代码治本**

## 四、问题
1. 怎么区分 "内存不足导致的 OOM"和"内存泄漏导致的 OOM"  ？

两者**共同点**是最终都堆占满、抛 OOM——所以"堆被占满"不是区分点。真正的区分看两点:

    1. **GC 后内存能不能回落**: 
        * **内存不足**:GC 后能正常降下来,只是业务量大、很快又涨满——内存是"够用就回落、不够才报错"
        * **内存泄漏**:GC 后**降不下来**,老年代持续走高
    2. **heap dump 里的对象分布**: 
        * **内存不足**:对象分布正常,占内存的都是业务**合理需要**的
        * **内存泄漏**:某一类对象**数量异常地多、持续增长**,顺引用链能找到一个"不该存在"的引用
