线程池执行流程核心逻辑：提交任务后，先判断核心线程池是否已满；若未满，创建核心线程执行任务；若已满，判断任务队列是否已满；若队列未满，将任务入队等待；若队列已满，判断最大线程池是否已满；若未满，创建非核心线程执行任务；若已满，执行拒绝策略。

## 二、核心问题解析
### 1. 为什么用 ctlOf / runStateOf / workerCountOf 这 3 个方法，不用两个独立字段（int runState + int workerCount）？
核心原因是线程池的状态变更与工作线程数量密切相关，若使用两个独立字段，高并发场景下无法实现原子修改，会导致状态判断错误（比如状态已变更但线程数量未同步，或线程数量变化但状态未更新），进而引发线程池调度异常。

### 2. 入队成功后，为什么还要检查池状态 + 兜底创建线程？
入队成功后仍需双重检查，核心是避免任务无法执行或执行异常，具体逻辑如下：

+ 入队后，线程池可能已被关闭，此时会尝试从队列中移除该任务；
+ 若移除任务成功，说明任务无法被执行，需调用拒绝策略；
+ 若移除任务失败，说明任务已在执行中，无需处理；
+ 若线程池处于运行状态，或移除任务失败，需检查是否有可用工作线程；若没有，兜底创建线程，否则任务会一直处于队列中无法执行。

### 3. addWorker(null, false) 第一个参数传 null 是什么意思？为什么要这么做？
addWorker 第一个参数的含义是：指定新线程启动后要执行的任务；

传 null 的原因：此时任务已成功入队，无需为新线程指定具体任务，只需创建新线程即可——新线程启动后，会自动从队列中获取任务并执行，避免任务无人处理。

### 4. execute 方法返回前，没有任何“任务被执行”的代码——任务是怎么真的跑起来的？
任务执行的核心逻辑在 addWorker 方法中：

+ addWorker 方法中创建好工作线程（Worker 实例）后，会调用线程的 start 方法；
+ JVM 启动新线程，自动调用 Worker 的 run 方法；
+ run 方法内部调用 runWorker(this)，线程会从队列中获取任务并执行，完成任务的实际运行。

### 5. Worker 继承 AQS 实现锁，但 ReentrantLock 也是基于 AQS 的——为什么 Worker 不直接持有一个 ReentrantLock 字段，而要自己继承 AQS？
核心原因是节省内存、避免无用资源占用：

+ 若线程池规模较大，会创建成百上千个 Worker 实例；
+ ReentrantLock 内部包含 Sync、ConditionObject 等字段，若每个 Worker 都持有一个 ReentrantLock，会占用大量内存；
+ Worker 只需简单的锁功能（控制线程中断、空闲状态），直接继承 AQS 只需使用一个 state 字段即可实现，无需额外引入 ReentrantLock，减少内存开销。

### 6. Worker 构造函数里 setState(-1)，为什么初始化成 -1？
目的是防止 Worker 刚创建、尚未开始运行时被中断：

+ Worker 真正开始运行后，会调用 unlock 方法将 state 从 -1 改为 0，表示 Worker 已启动完成，可被线程池调度；
+ 初始化为 -1，能屏蔽初始阶段的中断请求，避免 Worker 未就绪就被中断，导致任务无法执行。

### 7. Worker 实现的是不可重入锁（tryAcquire 只允许 0→1，持锁线程再 lock 也会失败）——为什么要禁止重入？
禁止重入是为了避免线程池误判 Worker 状态，防止任务被错误中断，具体场景如下：

若 Worker 是可重入锁，当任务执行过程中调用线程池的方法（如 setCorePoolSize）时，Worker 会重入自己的锁；此时线程池调用 interruptIdleWorkers() 遍历 Worker 时，会通过 tryLock() 判断 Worker 是否空闲，可重入锁会导致 tryLock() 成功（误判为空闲），进而错误中断正在执行任务的 Worker。

### 8. w.lock() / w.unlock() 的作用是什么？如果不加这把锁，会出什么问题？
+ w.lock()：给当前 Worker 加锁，修改 state 为 1，表示 Worker 正在执行任务（忙碌状态）；
+ w.unlock()：给当前 Worker 解锁，修改 state 为 0，表示 Worker 执行完任务（空闲状态）；

若不加这把锁，会导致线程池误判 Worker 状态：

+ 无法区分 Worker 是忙碌还是空闲，可能错误中断正在执行任务的 Worker；
+ 高并发下，多个线程可能同时操作同一个 Worker，导致状态混乱，引发任务执行异常。
